## Defects found and fixed

1. **Tagging anything returned a 500.** `CustomerTag::firstOrCreate(['slug' => …], …)`
   mass-assigns its lookup key, and `slug` is deliberately not fillable — it is derived from the
   name by the model. So `POST /customers` with tags, `PUT /customers/{id}` with tags, an import
   row with tags, and `POST /customer-tags` all threw `MassAssignmentException`. Tag creation is
   now one action, `Actions/UpsertCustomerTag`, which looks up by slug and creates by name;
   `SyncCustomerTags` delegates to it so the two entry points cannot drift.
2. **The API misreported consent on create.** `Customer` carried no model-level defaults, so the
   response to `POST /customers` was rendered from unset attributes and said
   `email.allowed: false` while the row in the database said the opposite — the answer changed on
   the next read. The migration's defaults are now mirrored in `$attributes` on the model, which
   also makes `allowsChannel()` correct on an unsaved instance (Notifications will ask that of
   whatever instance it is handed).
3. **The export audit recorded the wrong number.** `CustomerExportController` counted
   `Customer::query()->count()` — the whole book — while streaming a filtered file. An audit entry
   claiming four thousand customers were exported when the request asked for one tag is worse than
   no number, because it would be believed. Now `CustomerIndex::countMatching($filters)`.

Two smaller corrections:

- `RecordConsentRequest` dropped unknown channel names silently while its own docblock promised a
  validation error, so `{"channels": {"e-mail": true}}` answered 200 and changed nothing. Unknown
  channels are now a 422.
- `StoreCustomerTagRequest` accepted a name with nothing to slug. `"!!!"` and `"???"` both slug to
  the empty string, so the second one was a unique-index 500 rather than a validation error.
